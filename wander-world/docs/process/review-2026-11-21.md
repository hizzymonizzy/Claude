# Technical review: efficiency and technical debt (2026-11-21, alpha 0.11.0)

Scope: all of `engine/` and `app/` (about 7,300 lines of main code, 1,500 of tests, 56 engine tests + app tests).
Method: read the hot paths (rebuild, processing, resource search, map updates, the daily simulation loop), the
database schema and queries, and the threading. Findings are ranked by impact. Nothing here is a privacy issue.

## High impact

**H1. Raw GPS points are deleted after 90 days, so old walks can't be re-read under new rules.**
`dailyRun` prunes `track_point` older than 90 days. The world is replayed from derived data, which survives, but
when processing rules change (`PROCESSING_VERSION`) walks older than 90 days keep their old results ("too few
points"). The heat map needs every walk re-read at a finer hex (H3 res 12), so the history that gets pruned from
February onward would never get heat. *Fix:* stop pruning; store each finished walk's points compactly (encoded
polyline, about 2–5 KB per walk) and drop the per-point rows. Still on the phone only (ADR 0001).

**H2. The world is rebuilt too often, and concurrently.**
`rebuild()` replays every day from the start and reloads every table. It has no lock and no coalescing. Call sites:
app start (twice), end of every walk, background worker, daily worker (twice in a row in `dailyRun`), every purchase
and decision, and two settings toggles. Two overlapping rebuilds do double the work, and the slower one can publish
an older world last. *Fix:* one rebuild lane: a mutex plus "rebuild requested" coalescing (later requests merge into
one pending run), drop the redundant rebuilds in `dailyRun` and `onStart`, and log rebuild time under `[world]`.

**H3. The map recomputes fog on every world change.**
`MapScreen` recomputes the fog and explored geometry (a JTS union over every walked road and trail) whenever `world`
changes, including after a purchase, a decision or a banner change, though fog depends only on map layers and
waystones. *Fix:* separate effects: fog only when layers or waystones change; cheap layers (settlements, buildings,
trader) on world changes.

**H4. The resource search re-reads about 100 km² of map data every 20 seconds while recording.**
`nearestSources` loads all places, water, coast and field lines in a 2-ring of tiles (19 res-7 tiles) and decodes
every geometry each time. *Fix:* cache decoded geometry per tile, invalidated when a tile is re-fetched; only the
distance step runs every 20 s.

## Medium

**M1. Daily decay loops touch every road and cell every decaying day.** `protection()` updates all edges, trodden and
wake cells each day the ratio is below 0.8: days × roads. The weekly cooling of ADR 0008 runs once a week, a 7×
cut, and replaces this code.

**M2. `Repository.kt` does too much** (585 long lines: map data, processing, rebuild, resources, shop, diagnostics,
daily run). Already listed as known debt. *Fix:* split into `MapData` (tiles, Overpass), `Processor` (walks),
`WorldStore` (rebuild, layers, world flows), `Resources` (nearest sources), `Diagnostics`; `Repository` stays as a
thin facade so the UI doesn't change.

**M3. Rebuild queries presence cells twice** (`presenceTiles` and `nearTiles` are the same set) and decodes the
geometry of every landmark and edge on every rebuild. *Fix:* compute once; cache decoded geometry by id.

**M4. Overpass network code (`postWithRetry`, two-phase relations) is untested** (known debt). *Fix:* a fake HTTP
layer and tests for retry, 429 spacing, 502 fallback and the relation split.

## Low (clean-ups)

- **L1.** Two orphaned doc comments in `Repository.kt` (above `processPending`) describe functions that moved.
- **L2.** Fully qualified `world.wander.engine.*` names scattered through app code because the `world` property
  shadows the package; rename the property (`worldState`) and use imports.
- **L3.** `MapScreen` mixes map lifecycle, gathering dwell logic and layer updates (359 lines). Move dwell and gathering
  into a small state holder that can be unit-tested.
- **L4.** Unused `ground_meadow` texture path checks, and `Legend.kt` regeneration is a manual snippet: make it part of
  `tools/gen_legend.py`.

## What's in good shape
- Engine is pure, deterministic and well covered; the step order is explicit; per-source harvest is cached.
- Database: indexes on every filtered column; migrations exported and tested; processing guarded by a lock.
- Diagnostics: logging runs on a single background thread; each subsystem logs under its tag.
- Privacy gate (`tools/check.sh`) enforces hosts, permissions and exported components on every build.
